# チャット接続・モニタリング機能

## 目的（Why）

配信者がYouTube Live配信のチャットをリアルタイムで監視し、視聴者への対応（スーパーチャット確認、初見さん歓迎、メンバー識別等）を行うためのアプリケーションの核心機能。複数配信への同時接続により、コラボ配信や複数チャンネル管理にも対応する。

## 振る舞い（What）

### 接続

| 操作 | 結果 |
|-----|------|
| URL入力 + 「接続」クリック | YouTubeページをフェッチし、APIキー・Continuation Tokenを抽出。チャット監視タスクを起動。ConnectionResultを返却 |
| 同一URLに再接続 | 新規セッションとして接続（メッセージ復元なし）。配信内コメント数カウンタはDBから復元 |
| メンバー限定配信に認証なしで接続 | 接続失敗（Member Only エラー） |
| 無効なURLを入力 | 接続失敗（Invalid URL エラー） |

### メッセージ受信

| 状況 | 結果 |
|------|------|
| 新着メッセージ受信 | DBに保存、視聴者プロフィール更新、フロントエンドにTauriイベント発行 |
| 同じ接続で既に受け取った message_id が再び届いた | 捨てる。DB保存・配信内コメント数・GUI・WebSocket・TTS のいずれにも流さない |
| 別の接続で受け取った message_id が届いた | 新着として扱う（重複の判定は接続ごと） |
| 同じ配信に再接続し、前の接続で受け取ったコメントが同じ id で届いた | 別の接続のメッセージとして並べる（同じコメントが2つ並ぶ）。一覧・視聴者パネルのキーや選択の判定も `connection_id:message_id` で行い、message_id だけでは扱わない |
| コメントが途切れた（取得に成功したが新しいメッセージが無い） | 次の取得までの待ちを少しずつ延ばす。新しいメッセージが届いたら 1.5秒に戻す（「取得の間隔」） |
| YouTube から「チャットが更新された」通知が届いた | 待ちを打ち切って取りに行く。ただし前回の取得から 1.5秒は空ける（「プッシュ通知」） |
| 通知を受けられない・途中で壊れた | ポーリングだけで取り続け、間を空けて通知につなぎ直す。画面には何も出さない（「プッシュ通知」） |
| 取得に失敗（タイムアウト・ネットワークエラー・HTTPエラー・JSONでない応答） | warnログを出力し、次のポーリングで再試行。続けて失敗したら待ちを延ばし、15回続いたら切断する（「取得に失敗したとき」） |
| 取得の応答を待っている間に切断 | 応答を待たずに止まり、セッションを閉じる |
| DB保存エラー | warnログを出力し、メッセージ処理は継続 |

### 初見さん判定

| 条件 | 判定 |
|------|------|
| その配信者チャンネルで初めてコメントした視聴者（`viewer_streams`の最古video_idが現在のvideo_id） | `is_first_time_viewer = true` |
| 過去に別の配信でコメント済み | `is_first_time_viewer = false` |
| 配信者Aで初見 + 配信者Bでは常連 | 配信者ごとに独立判定 |
| 視聴者を特定できないギフト（`channel_id == ""`） | `is_first_time_viewer = false` |
| メンバーシップギフトの受け取り | `is_first_time_viewer = false`（コメントではない。「メンバーシップギフトの受け取り」） |

### ギフト

視聴者がジュエルで送るギフト（メンバーシップギフトとは別物）。InnerTube では `giftMessageViewModel` で届き、channel_id とタイムスタンプが付かない。

**パース:**

| 入力 | 結果 |
|------|------|
| `text` = `sent Press F for 10 Jewels` | gift_name = `Press F`、jewel_count = `Some(10)` |
| `text` = `sent Press F for 1 Jewel` | gift_name = `Press F`、jewel_count = `Some(1)` |
| `text` = `sent Hiding` | gift_name = `Hiding`、jewel_count = `None` |
| `text` が `sent ` で始まらない、または空。`giftImageA11yLabel` = `@x sent a gift, Hiding` | gift_name = `Hiding`、jewel_count = `None` |
| `text` からもラベルからも名前が取れない | gift_name = `ギフト`、jewel_count = `None`。warn ログを出す |
| `authorName` = `@viewer-a1b `（末尾に空白） | author = `@viewer-a1b` |
| `giftImage.sources[].url` = `//www.gstatic.com/...=w480-h480` | gift_image_url = `https://www.gstatic.com/...=w480-h480`（幅が最小の source を使う） |
| `giftImage` が無い | gift_image_url = `None` |
| タイムスタンプ | 受信した時刻 |
| バッジ・メンバー情報 | 無し（is_member = false、badges は空） |

ジュエル数は配信者本人としてログインした接続でのみ本文に入ると見られる（観測は3件: ログインあり2件はジュエル数あり、ログインなし1件は無し）。

**視聴者の特定（handle → channel_id）:** 次の順に探し、最初に見つかったものを使う。

1. その接続で受信済みのメッセージの author → channel_id（同じ handle は最後に見たもの）
2. DB: その配信者の `viewer_profiles` で `display_name` が handle と完全一致するもの。一致が2件以上なら特定しない

| 状況（配信者 UCown） | 結果 |
|------|------|
| 同じ接続で `@viewer-a1b`（UCa1b）がコメント済み | channel_id = UCa1b |
| 接続中は未発言、DB の UCown 配下に `@viewer-a1b` → UCa1b | channel_id = UCa1b |
| DB の UCown 配下に `@viewer-a1b` が2件（UCa1b・UCzzz） | 特定しない |
| どこにも無い | 特定しない |
| 配信者の channel_id が分からない接続 | 1 だけで探す |

| 特定の結果 | 扱い |
|-----------|------|
| 特定できた | 通常のメッセージと同じ（viewer_profiles・viewer_streams・初見判定・配信内コメント回数・視聴者情報パネル） |
| 特定できない | `channel_id = ""` で保存・表示。viewer_profiles・viewer_streams は更新せず、初見判定は false、配信内コメント回数は数えない（`None`）。視聴者情報パネルは開かない |

保存済みのギフトの channel_id を後から埋めることはしない。

**ジュエル数を取れない接続の知らせ:**

| 状況 | 結果 |
|------|------|
| jewel_count = None のギフトを受信 | 接続一覧のその接続に注記「ジュエル数を取得できません。配信者本人としてログインした接続でのみ取得できます」を出す |
| jewel_count がある ギフトだけを受信 | 注記を出さない |
| 切断・再接続・F5リロード | 注記は消える。再びジュエル数の無いギフトを受けたら出る |

ダイアログや通知は出さない（配信中の操作を妨げない）。

### メンバーシップギフトの受け取り

視聴者が、他の人が贈ったメンバーシップを受け取ったお知らせ。InnerTube では `liveChatSponsorshipsGiftRedemptionAnnouncementRenderer` で、受け取った人 1 人につき 1 件届く。贈った人のお知らせ (`membership_gift`) の後に続く (実測: 1 件のギフトで 1.3 秒後、同じ応答の中)。種別は `membership_gift_redemption`。

メンバーシップギフトを大量に贈る人がいるチャンネルでは、受け取りのお知らせで流れが埋まる。そのため受け取りを 1 件ずつ行にせず、画面では贈った人の行にまとめる。お礼の対象は贈った人なので、受け取りはお礼の一覧に入れない (シフィさん、2026-10-12)。

**パース:**

| 入力 | 結果 |
|------|------|
| `authorName.simpleText` = `@viewer-a1b`、`authorExternalChannelId` = `UCa1b` | author = `@viewer-a1b`、channel_id = `UCa1b` (受け取った人) |
| `message.runs` = `received a gift membership by ` + `@gifter-x9` (`bold: true`) | content = `received a gift membership by @gifter-x9`、gifter = `@gifter-x9` (最初の太字の run) |
| `message.runs` に太字の run が無い | gifter = `None` |
| `message` が無い | content = `""`、gifter = `None` |
| タイムスタンプ・アイコン | `timestampUsec`・`authorPhoto.thumbnails[0]` |
| バッジ・メンバー情報 | バッジは届かないので読まない (保存は NULL = 不明)。is_member = true |

**扱い:**

| 項目 | 扱い |
|------|------|
| 流れ | 1 件ずつの行にしない。贈った人の行にまとめる (下の「まとめ方」) |
| お礼の一覧・流れたものの欄 | 入れない |
| 保存 | 1 件ずつ messages に保存する。viewer_profiles・viewer_streams は更新しない (受け取った人のコメントではない。viewer_streams を更新すると、後の配信でその人が初めてコメントしたときに初見と判定されなくなる) |
| 配信内コメント回数・初見判定 | 数えない (`in_stream_comment_count` = None、`is_first_time_viewer` = false)。受け取った人がその後に初めてコメントすると `#1` |
| 読み上げ | 読まない (大量に配られると読み上げが埋まる。贈った人のギフトは今までどおり読む) |
| WebSocket | 1 件ずつ `MembershipGiftRedemption` で送る (まとめるのは画面だけ) |
| フィルタ | 「メンバーシップ」と一緒に隠す |
| 状態の行の統計 | 件には数えない (行ではない)。人には数える (一覧に名前が出る) |
| セッションの統計 (`memberships`) | 数えない (贈った人のギフトの件数で数えている) |

**まとめ方:**

受け取りは、同じ接続で、届いた時点で最後の「まとめ先」にまとめる。まとめ先は、author が gifter と同じ `membership_gift` の行と、下の「まとめ先が無い」で作った受け取りの行。

| 状況 | 結果 |
|------|------|
| `@g` の「メンバーシップを 3 件ギフト」の後に、受け取り A・B・C が届いた | 贈った人の面の本文の下に「受け取った人 3: A、B、C」(届いた順)。流れの行は増えない |
| 受け取り A が届いた時点で、まとめ先が無い (接続する前に贈られた・gifter が分からない) | A を標準の行 (優先順位 5) で出す。札は「ギフトで加入」、本文は content。続く同じ gifter の受け取り B・C はこの行にまとめ、「受け取った人 3: A、B、C」を足す (受け取った人が 1 人のうちは出さない) |
| gifter が分からない受け取りが続いた | gifter が分からないもの同士で、同じように最後の受け取りの行にまとめる |
| `@g` が 2 回贈った | 受け取りは、届いた時点で最後の `@g` のまとめ先に入る |
| 別の接続の `@g` のギフト | まとめない (接続ごと) |
| 受け取った人の名前 | 省略せず折り返す。読み仮名は出さず、名前は押せない (行を押すと、その行の視聴者のパネルが開く) |
| 「コメントを消す」の後に届いた受け取り | まとめ先が無いので、新しい受け取りの行になる |
| 贈った人の行が表示件数で外れた・フィルタで隠れた | まとめた受け取りも一緒に隠れる |

例: `@g` が 50 件贈り、受け取りが 50 件届く → 流れには `@g` の「メンバーシップを 50 件ギフト」の面が 1 つだけあり、面の中の「受け取った人 50: …」が届くたびに伸びる。お礼の一覧には `@g` の 1 件だけ。読み上げは `@g` のギフトの 1 回だけ。

### ライブリアクション

視聴者がチャット欄から送る絵文字リアクション（❤ 🎉 😄 💯 😳 など）。チャットメッセージではなく、送り主は分からない。InnerTube では応答の `frameworkUpdates.entityBatchUpdate.mutations[].payload.emojiFountainDataEntity` で、前回の更新からの差分として届く（変化が無いときは届かない）。

**パース（1つの `emojiFountainDataEntity` → 1つの ReactionUpdate）:** `reactionBuckets[]`（1秒単位の区切り）を合算する。

| 入力 | 結果 |
|------|------|
| `updateTimeUsec` = `1790422357025983`、バケット2つ（どちらも `duration.seconds` = `1`、`reactionsData` = `[{"unicodeEmojiId":"🎉","reactionCount":4}]`） | update_time_usec = 1790422357025983、duration_seconds = 2、counts = {🎉: 8}、total = 8 |
| バケット1つ（`reactionsData` = `[{"unicodeEmojiId":"❤","reactionCount":3},{"unicodeEmojiId":"😄","reactionCount":1}]`）とバケット1つ（`totalReactions` = 0、`reactionsData` 無し） | duration_seconds = 2、counts = {❤: 3, 😄: 1}、total = 4 |
| すべてのバケットが `totalReactions` = 0 | 捨てる（保存もイベントも出さない） |
| `unicodeEmojiId` か `reactionCount` が無い要素 | その要素だけ無視する |
| `duration` が無いバケット | 1秒として数える（観測ではすべて1秒） |
| `updateTimeUsec` が無い | 捨てる。warn ログを出す |
| 同じ接続で、update_time_usec が前回受けた値以下 | 捨てる（同じ更新の再送） |

- total は counts の合計（`totalReactions` は使わない。件数の出どころを1つにする）
- `intensityScore` は使わない（観測では件数ありで 0.75、0件で 1 の2値だけで情報が無い）
- 1回の更新の中のバケットの時間順は応答から判別できないため、1秒ごとの時刻は付けない。分析の細かさは更新ごと（観測では間隔の中央値1.6秒）

**扱い:**

| 項目 | 扱い |
|------|------|
| DB | `reactions` テーブルに更新×絵文字ごとに1行（[08_database.md](08_database.md)） |
| チャット欄 | メッセージとしては流さない。主の配信の累計を状態の行に出す |
| 読み上げ | しない |
| WebSocket | `Reaction` を配信する（[03_websocket.md](03_websocket.md)） |
| 視聴者・初見判定・配信内コメント回数 | 関係しない（送り主が分からない） |

**状態の行のリアクション:** 主の配信 (「配信中の画面」の「主の配信と相手の配信」) の累計だけを、状態の行の右端に控えめに出す。
相手の配信のリアクションは出さない (記録・WebSocket には流す)。勢い (/分) は出さない (配信中に見て行動が変わる情報ではない。シフィさん、2026-10-09)。

```
● 1,820 件  48/分  312 人                 ❤ 430  🎉 418  😄 94
```

| 項目 | 仕様 |
|------|------|
| 累計 | 配信（video_id）単位の絵文字別件数。同じ配信に再接続したら、DB から続きを数える |
| 並び・数 | 多い順に 3 つまで。絵文字は色を抜く (控えめに)。4 つ目以降も含めた全部をヒントと読み上げ用の名前で出す |
| 表示条件 | 主の配信に1件以上のリアクションがあるとき |

| 状況 | 結果 |
|------|------|
| 主の配信に 🎉4 → ❤3 | `🎉 4  ❤ 3` |
| 主の配信に ❤430・🎉418・😄94・💯56 | `❤ 430  🎉 418  😄 94`。💯 56 はヒントにだけ出る |
| 相手の配信にだけリアクションがある | 何も出さない |
| F5リロード | 累計を `get_connection_reactions` で読み直す |
| 同じ配信に再接続 | 累計は DB の続きから |
| 主の配信を切断し、他の接続が残った | 新しい主の配信の累計を出す |

### 多接続

| 操作 | 結果 |
|------|------|
| 2つ目以降のURLで「接続」クリック | 追加接続。全接続のメッセージをグローバルバッファに統合表示 |
| 接続済みと接続中を合わせて32件あるときに「接続」 | 接続を拒否する（「同時接続数の上限（32）に達しています」）。同時に「接続」が続いても32件を超えない。切断・接続失敗で枠が空く |
| 「全切断」クリック | 接続済みの全接続を一括切断。接続中（`connecting`）のものは残り、成立したら一覧に出る。切断の途中で成立した接続も止めずに残す（押した時点の接続だけを切る） |
| 接続中（`connecting`）のエントリ | 切断ボタンは押せない。接続が成立するか失敗するまで待つ（接続処理には HTTP タイムアウトがあるので待ち続けない） |
| 接続が成立した | URL 入力欄を空にする。ただし欄の内容がその接続の URL から変わっていたら残す |
| F5リロード | バックエンド接続は維持。`get_connections`で状態を復元し、新着メッセージを正常受信 |
| コメントをクリックして視聴者パネルを開く | そのコメントが届いた接続の配信者のもとで視聴者を引き、読み仮名・メモもその配信者のもとに保存する（TTS が読み仮名を引く配信者と同じ）。最初の接続の配信者ではない（「視聴者情報パネル」の「どの配信者のもとで開くか」） |

### 配信中の画面

デザインの前提は [docs/design/brief.md](../design/brief.md)、見た目の値は [docs/design/tokens.md](../design/tokens.md)。
配信中 (特にゲーム中) は配信者が liscov を操作できないので、**配信中の目的は操作ゼロで達成できる**ことを基準にする。
試作は `src/routes/design-proto/c` (方向性 C「流れ型」、2026-10-08 に選定)。

**構成 (上から):**

```
┌───────────────────────────────────────────┐
│ 💬 👥 ⚙  │ ●配信者A ×  ●あおば ×  +   ∨   │ ← 上の行 (タブ・接続の札・操作パネルの開閉)
├───────────────────────────────────────────┤
│ 操作パネル                                │ ← 開いたときだけ (「操作パネル」)
├───────────────────────────────────────────┤
│                                           │
│ コメントの流れ (最新が下)                 │ ← 残りの高さすべて
│                                           │
├───────────────────────────────────────────┤
│ 流れた新規さん 3                          │ ← あるときだけ。高さの 1/8 まで (ドラッグで変えられる)
├───────────────────────────────────────────┤
│ この配信のスパチャ等の一覧 流れた 5 [概要|詳細]│ ← 自分の配信のスパチャ等があるときだけ。概要 = 流れたもの、詳細 = 時刻順の全件。高さの 1/8 まで (ドラッグで 1/2 まで)
├───────────────────────────────────────────┤
│ ● 1,820 件  48/分  312 人   ❤ 128 🎉 31  │ ← 状態の行
└───────────────────────────────────────────┘
```

- 接続・切断・フィルタ・表示の設定などの操作は、操作パネルにまとめ、配信中は隠しておける
- 配信中に固定で場所をとる UI (上の行と状態の行) は、高さの 15% 以下 (ブリーフ §3)

**上の行と操作パネル:** (方向性の試作は `src/routes/design-proto/frame` の C、2026-10-09 に選定。名前はシフィさん)

| 状況 | 結果 |
|------|------|
| いつも | 上の行に、画面のタブ (チャット・視聴者・設定の 3 つ。アイコン。名前はヒントと読み上げ用の名前で出す)、接続の札、配信に接続する「+」、操作パネルを開け閉めする矢印 (右端、∨ / ∧) を出す |
| 接続の札 | 接続ごとに「状態の点 + 配信者名 + 切断 (×)」。点は接続済みなら success の色、接続の途中・切断の途中は控えめな色 (取得の失敗が続いて切断した接続は札から消え、状態の行にエラーを出す)。主の配信の名前は太字。配信タイトルはヒントで出す |
| 接続の札が上の行の幅に収まらない | 札の列だけを横にスクロールする (上の行は 1 行に保つ)。マウスのホイールの上下でも横にスクロールする (ブラウザのタブの列と同じ。シフィさん、2026-10-10)。トラックパッドの左右・Shift + ホイールは今までどおり横に動く。収まっているときはホイールに何もしない |
| 矢印を押す・「+」を押す | 操作パネルが開く (「+」は配信の URL の入力に移る)。もう一度矢印を押すと閉じる |
| チャット以外のタブで「+」・矢印を押す | チャットのタブに移って操作パネルを開く (操作パネルはチャットのタブにだけある) |
| 操作パネルの中身 | 接続の一覧 (配信者名・配信タイトル・ジュエル数の注意・切断・全切断)、配信に接続する (URL・すべてのコメントを取るか・「接続」のボタン)、表示の設定 (文字の大きさ・時刻・表示件数・種類のフィルタ・検索・コメントを消す)、ログインの状態 (01_auth.md「AuthIndicator.svelte」。押すと設定のログインを開く)、WebSocket サーバーの状態、「接続したら操作パネルを隠す」の設定 |
| 「すべてのコメントを取る」 | 今の「チャットモード」と同じ。接続中のすべての配信とこの後の接続に効き、設定に残る (シフィさん、2026-10-09) |
| 操作パネルが高さに収まらない | 操作パネルの中でスクロールする。流れは高さの半分以上を残す |
| 配信に接続した (接続に成功した) | 「接続したら操作パネルを隠す」が有効 (既定) なら、操作パネルを閉じる。無効なら開いたまま |
| 「接続したら操作パネルを隠す」を無効にした | 操作パネルは手で閉じるまで開いたまま (コラボで続けて接続する人、開いたままが好みの人のため。シフィさん、2026-10-09) |
| 未接続 (接続の途中を含む) で、表示するコメントも無い | 操作パネルの開閉によらず、流れの場所に配信に接続する欄を出す (配信の準備なので操作してよい。接続の途中も出したままにして、失敗したら入力をそのまま直せるようにする)。このとき操作パネルには接続する欄を出さない (二重にしない) |
| 切断したが、コメントが残っている | 流れを出したまま (配信後のお礼・確認のため)。次に接続するときは操作パネルを開く |
| フィルタ・表示件数で一部を隠している | 操作パネルを閉じていても、状態の行に「表示中 N / 全 M 件」を出す (隠していることを忘れない) |
| 540 幅 | ボタンの文字を縦に折らない。中身は折り返して並べ、省略しない |

**主の配信と相手の配信:**

この節の「自分の配信」は**主の配信**のこと。主の配信は最初の接続で決め、配信者本人のチャンネルかどうかは問わない
(テストで他の人の配信に接続することもある。シフィさん、2026-10-09)。

| 状況 | 結果 |
|------|------|
| 接続が 1 つ | すべて主の配信のもの (他の人の配信に接続していても同じ) |
| 接続が 2 つ以上 | 最初の接続 (`broadcasterChannelId` と同じ) が主の配信。それ以外は相手の配信 |
| 主の配信を切断し、他の接続が残った | 残った接続のうち、いちばん先に接続したものが主の配信になる |

**優先順位と強調** (ブリーフ §2。判定は `src/lib/design/priority.ts` の `messagePriority`):

| コメント | 優先順位 | 流れの中での表し方 |
|------|------|------|
| 自分の配信のスパチャ・スーパーステッカー・ギフト・メンバーシップ (ギフト・マイルストーンを含む) | 1 | 面 (スパチャ等は YouTube のティアの色、メンバーシップ系は member の色) |
| 新規さんの、その配信での初回 (`is_first_time_viewer` かつ `#1`) | 2 | 薄い背景 + 塗りの印「初見」 |
| 新規さんの 2 回目以降 | 3 | 枠だけの印「初見」(背景なし) |
| 常連の、その配信での初回 (`#1`) | 4 | 名前の前の小さい点 |
| それ以外 (配信内コメント回数が分からないものを含む) | 5 | 印なし (標準) |
| 相手の配信のスパチャ等 | 5 | 標準の行に金額 (またはメンバーシップの種類) の枠つきの札を添える。お礼の対象ではない |
| 相手の配信の新規さん・常連 | 自分の配信と同じ (2〜5) | 同じ表し方 + 配信元の行 |
| メンバーシップギフトの受け取り (まとめ先が無かったもの) | 5 | 標準の行に枠つきの札「ギフトで加入」。お礼の対象ではない (「メンバーシップギフトの受け取り」) |

**1 行の形:**

| 状況 | 結果 |
|------|------|
| 通常のコメント | 2 段にする。1 段目に名前 (と読み仮名・印・バッジ・`#N`・時刻) を小さく、2 段目に本文。本文の頭はどの行もアイコンの右の同じ位置でそろう (斜め読みで本文の頭を縦にたどれるように。名前の長さで本文の書き出しが左右にずれると、視線が横に振られる)。試作 `src/routes/design-proto/scan` の A「名前の行 + 本文」、2026-10-10 に選定。名前を決まった幅の列に置く案 (B・D) は、長い名前の人が頻繁にコメントすると毎回列の中で折り返して行が伸びるので採らない |
| 長い本文・長い名前 | 折り返して全文を出す。流れ・流れたものの欄・スパチャ等の一覧の詳細のどこでも、省略 (`…`) しない (省略された文字を読むには操作が要る) |
| 相手の配信のコメント | 名前の行の上に 1 行を足して配信者名を出す (3 段になる。色ではなく文字で見分ける。540px 幅でも読める)。名前の行は自分の配信のコメントと同じ形のまま。配信者名は省略せず、長ければ折り返す。強さは変えない。以前は名前の前に札で出していたが、配信者名が長いと名前の行がどのみち 2 行に折り返すので、1 行を分けた (シフィさん、2026-10-10) |
| 読み仮名が登録されている視聴者 | 名前の横に小さく出す |
| メモが登録されている視聴者 | 本文の下に控えめな 1 行で、「メモ」の札とメモの全文を出す。その人のコメントには毎回出す (反応するときに、操作せずにどんな人か思い出せるように)。流れ・流れたものの欄の全文の行・スパチャ等の一覧の詳細のどこでも出し、流れたものの欄の短い札には出さない。長いメモも折り返して省略しない。スパチャ等の面では面の中の本文の下。メモは読み上げない (試作 `src/routes/design-proto/memo` の B「本文の下」、2026-10-10 に選定) |
| メンバーのコメント | 名前を緑の文字にし、メンバーバッジの画像を名前の横に出す (YouTube と同じ。背景・枠は付けない)。バッジの画像が無ければ「メンバー」の文字の札。新規さんの初回の行では名前は通常の色 (薄い背景の上で緑が読みにくいため) |
| モデレーター・認証済み | 名前の横に小さい印 (🔧・✓) |
| 時刻 | 表示の設定で消せる (今と同じ) |
| 文字の大きさ | 表示の設定 (10〜24px) を流れ・欄・一覧のコメントの文字に使う (今と同じ) |

**流れたもの (流れて画面の外に出た優先順位 1・2):**

流れたものの欄は「流れた新規さん」と「この配信のスパチャ等の一覧」の 2 つ。「この配信のスパチャ等の一覧」は概要 (流れたもの) と詳細 (時刻順の全件) を切り替えられる (下の「配信の最後のお礼」)。この節の「欄」の振る舞いは、断りがなければ両方の欄 (スパチャ等の一覧は概要) に当てはまる。

| 状況 | 結果 |
|------|------|
| 自分の配信のスパチャ等が、流れの画面の外 (上) に出た | 「この配信のスパチャ等の一覧」の概要の先頭に出る |
| 新規さんの初回コメント (相手の配信のものを含む) が画面の外に出た | 「流れた新規さん」の欄の先頭に出る |
| 欄の見出し | 流れとの境がちらっと見て分かるように、見出しを一段濃い帯にして名前と件数を太字で出し、帯の上端にアクセント色の線を引く (2026-10-11 の配信で、今の見出しでは境が分かりにくかった。シフィさんが案 B を選んだ) |
| 欄の中の並び | 新しいものが上。新しい 2 件は全文の行 (時刻・金額・名前・本文)、それより前は「● 金額 名前」(新規さんは「初見 名前」) の短い札を折り返して並べる |
| 手でスクロールして戻り、そのコメントがまた画面に見えた | 欄から外れる (見えているものを二重に出さない) |
| 時間がたった | 消えない (最後のお礼のために残す) |
| 欄の中身が高さの上限 (既定 1/8) を超えた | その欄の中でスクロールする。もう一方の欄の高さは変わらない |
| 欄の上の境目をドラッグする | その欄の高さの上限が変わる (上へ引くと高く)。「流れた新規さん」と「この配信のスパチャ等の一覧」は別々に変えられる。スパチャ等の一覧の上限は概要と詳細で共通 (どちらで変えても同じ値) |
| 中身が上限より少ない | 中身の高さまで縮む (今と同じ)。ドラッグで広げても中身の高さで止まる (見えている高さを覚える) |
| 変えられる範囲 | 下限は見出しと 1 行が見える高さ、上限はコメントの流れの部分 (`ChatDisplay`) の高さの 1/3 (シフィさん、2026-10-10)。「この配信のスパチャ等の一覧」だけは 1/2 まで (詳細で全件を見るため。以前のお礼の一覧の高さ。シフィさん、2026-10-12) |
| ウィンドウの大きさを変えた | 高さに対する割合を保つ |
| 境目をダブルクリックする | 既定 (1/8) に戻す (シフィさん、2026-10-10) |
| 境目にフォーカスして ↑ / ↓ | 少しずつ (高さの 1/50 ずつ) 高く / 低くする |
| 覚えておく | ドラッグを離したとき・ダブルクリック・キーで変えたときに設定 (`chat_display.flowed_*_height_ratio`、09_config) に保存し、次の起動でもその高さで出す |

| 相手の配信のスパチャ等 | どちらの欄にも入らない (スパチャ等の一覧の詳細にも入らない) |
| フィルタで隠しているもの | 欄に入らない (流れに出ていないので、流れてもいない)。スパチャ等の一覧の詳細はフィルタによらない |
| 「コメントを消す」 | 欄も空になる |

例 (欄の高さ): 流れの部分が 800px、「流れた新規さん」の中身が 300px → 既定の上限は 100px (1/8)。境目を 60px 上へ引くと 160px (0.2) になり、離すと 0.2 を覚える。さらに 200px 上へ引いても 266px (1/3) で止まる。中身が 120px しかなければ 120px (0.15) で止まる。ウィンドウを縮めて流れの部分が 600px になると、0.2 なら 120px。境目をダブルクリックすると 100px (0.125) に戻る。「この配信のスパチャ等の一覧」なら 200px 上へ引くと 360px (0.45) まで伸び、400px (1/2) で止まる

例 (2 段): `しおこんぶ #8 21:26` の下に `いったん回復しよう`、`夜ふかし研究会 (よふかし) #9 21:29` の下に `ボス戦 2 回目`。名前の長さが違っても、`いったん回復しよう` と `ボス戦 2 回目` の書き出しは同じ位置。

例 (メモ): 「しおこんぶ」にメモ「ネタバレしがち。注意」を登録してある → 本文 `いったん回復しよう` のすぐ下に `[メモ] ネタバレしがち。注意`。次のコメント `いけるいける` の下にも同じ 1 行が出る。

例 (640×1080): ¥10,000 の赤スパのあとにコメントが 40 件来て流れの画面から外れた → 「この配信のスパチャ等の一覧」の概要の先頭に `21:17 ¥10,000 ねむいペンギン 遅れてきました！…` が全文で出る。

**配信の最後のお礼:**

「この配信のスパチャ等の一覧」の欄で、概要と詳細を切り替える。どちらも自分の配信のスパチャ等で、同じ意味のものを同じ場所で詳しさだけ変える (シフィさん、2026-10-12)。
以前は「流れたスパチャ等」の欄と別にお礼の一覧があり、上端に開くとどこに出たか見失いやすく、下端の帯にすると欄と似た見た目で振る舞いが違って分かりにくかった。

| 状況 | 結果 |
|------|------|
| 欄を出すとき | 自分の配信のスパチャ等が 1 件でもあるとき。概要で流れたものが 0 件 (全部画面に見えている) なら見出しの 1 行だけ |
| 見出し | 「この配信のスパチャ等の一覧」と件数、右端に「概要」「詳細」の切り替え (選んでいる方が分かる)。件数は概要なら「流れた N」、詳細なら「全 N 件・時刻順」 |
| 概要 | 流れたもの (上の「流れたもの」の欄の並び。新しいものが上、新しい 2 件は全文、それより前は短い札) |
| 「詳細」を押す (1 手) | 欄の中身が時刻順の全件になる (古いものが上、先頭から見える。全件を全文の行で)。欄の場所は変わらず、高さの上限も概要と共通 (中身が多ければ上限まで伸びる)。上にコメントの流れと「流れた新規さん」の欄が残り、最新のコメントも見える |
| 詳細の中身 | 自分の配信の優先順位 1 を時刻順。画面のメッセージ一覧にあるもの (「コメントを消す」で消える)。フィルタ・表示件数によらない |
| 「概要」を押す | 流れたものに戻る |
| 起動・F5 | 概要 (どちらを選んでいたかは覚えない。次の配信の始めに詳細のままにならないように) |

例 (お礼の一覧): 自分の配信のスパチャ等が 6 件、そのうち 2 件が流れた → 欄の見出しは「この配信のスパチャ等の一覧 流れた 2 [概要|詳細]」で、流れた 2 件が新しいものを上に並ぶ。「詳細」を押すと、同じ欄の中身が 6 件の時刻順 (古いものが上) になり、見出しの件数は「全 6 件・時刻順」になる。「流れた新規さん」の欄とコメントの流れは欄の上に残る。「概要」を押すと流れた 2 件に戻る。

例 (流れたものが無い): 自分の配信のスパチャ等が 3 件あり、全部画面に見えている → 欄は見出しの 1 行「この配信のスパチャ等の一覧 流れた 0 [概要|詳細]」だけ。「詳細」を押すと 3 件が時刻順に並ぶ。

**視聴者の読み仮名・メモ (視聴者情報パネル):** (置き方の試作は `src/routes/design-proto/viewer` の C「行の中で広げる」、2026-10-09 に選定)

読めない名前に気づいたら、合間にそのコメントを押してすぐ読み仮名を打てるようにする (ブリーフ §4「コメントから 2 手で入力を始められる」)。
パネルは押した行のすぐ下に広がるので、誰の情報を打っているかが位置で分かる。打っている間は流れが止まる。

| 状況 | 結果 |
|------|------|
| 流れのコメントを押す (1 手) | その行のすぐ下に視聴者情報パネルを広げ、読み仮名の欄にフォーカスする (読み込みが終わりしだい打てる)。流れは止まり、最新から離れる |
| 流れたものの欄 (スパチャ等の一覧の詳細を含む) のコメントを押す | 流れのそのコメントまで移り、その下に広げる。流れに無い (フィルタで隠している・表示件数で外れた) ときは、押した行のすぐ下に広げる |
| パネルの中身 | 名前、読み仮名、メモ、保存、「この人のコメント N 件」(畳んである。押すと開く)、閉じる (×)。接続が 2 つ以上なら、どの配信者のもとに保存するかを配信者名の札で出す |
| 読み仮名・メモの欄で Enter・「保存」を押す | 読み仮名とメモを保存して閉じる。画面にある同じ視聴者 (同じ配信者のもと) の行の名前の横に、すぐ読み仮名が出て、本文の下にメモが出る (空にしたら消える。これが保存できた印。読み上げ用に「保存しました」も伝える) |
| 日本語入力の変換を確定する Enter | 保存しない (確定だけ) |
| × を押す・Esc | 保存せずに閉じる |
| 閉じたとき | 開く前に最新を追っていたら最新に戻る (配信中に止まったままにしない)。開く前から離れていたら、離れたまま (30 秒で戻る) |
| 開いている間に別のコメントを押す | 前のパネルを閉じ (保存していない内容は捨てる)、押した行の下に開き直す |
| 「この人のコメント」の行を押す | 流れのそのコメントへ移り、3 秒強調する。パネルは元の行の下のまま |
| パネルの欄にフォーカスがある・保存していない変更がある | 30 秒で最新に戻らない (打っている途中で流れていかない) |
| フォーカスが外れ、変更も無いまま 30 秒、流れの上で操作が無い | 最新に戻り、パネルを閉じる |
| 押した行が流れから無くなった (コメントを消す・表示件数で外れた) | パネルを閉じる |

**自動スクロール:**

| 状況 | 結果 |
|------|------|
| 新着が来た (最新を表示中) | 最新までスクロールする |
| 手でスクロールして最新から離れた | 自動スクロールが止まる |
| 最新から離れたまま 30 秒、流れの上で操作 (スクロール・クリック・マウスの移動) が無い | 最新に戻り、自動スクロールを再開する (戻し忘れても配信中に止まったままにならない)。ただし視聴者情報パネルで打っている間は戻らない (上の「視聴者の読み仮名・メモ」) |
| 最新から離れている間に、流れに出る優先順位 1・2 (自分の配信のスパチャ等・新規さんの初回) が届いた | 「最新へ」に件数を添える (例: 「最新へ スパチャ等 2・新規さん 1」。0 件の種類は出さない)。最新に戻ると数え直す (止まっている間に来たものに気づけるように。シフィさん、2026-10-09) |
| 手で最新までスクロールした | 自動スクロールを再開する |
| 最新から離れている | 流れの右下に「最新へ」のボタンを出す。押すと最新に戻り、自動スクロールを再開する。ボタンはコメントの行に重ねない (離れている間だけ、流れの下端にボタンの高さの帯をとり、その右に置く。見ている行の位置は動かさない。シフィさん、2026-10-09) |
| 「最新へ」のボタン | 自動で最新に戻るまでの残り時間を、ボタンの中の帯が縮んでいく動きで表す。流れの上で操作すると満ちた状態からやり直す (シフィさん、2026-10-09)。動きを減らす設定 (`prefers-reduced-motion`) では、帯を動かさず残りの秒数を文字で出す |
| 自動スクロールを止める設定 | 無い (止まったままにならないことを優先する。以前の「自動スクロール」のチェックと「最新に戻る」のボタンは外した) |

**状態 (異常のときだけ目立つ):**

状態の行 (下端の 1 行) に、左から 点・コメント数・直近 1 分のコメント数・コメントした人数、右端に主の配信のリアクションの累計 (絵文字は色を抜く) を控えめに出す。

| 状況 | 結果 |
|------|------|
| 接続中 | 状態の行の左端の小さい点 (success の色) だけ |
| 接続が切れた・取得の失敗が続いている・接続に失敗した | 状態の行を error の面にし、理由を文字で出す (例: 「チャットの取得に15回続けて失敗したため切断しました」)。理由は折り返して全文を出す |
| エラーの「閉じる」を押す・次に接続する | エラーを消して、ふだんの状態の行に戻す |
| ログインのセッションが切れた・ストレージエラー (01_auth「AuthIndicator」の異常) | 操作パネルを閉じていても、ふだんの状態の行の上に 1 行足して、error の色で「ログイン: セッション切れ」・「ストレージエラー」を出す (ふだんの行の並びは動かさない。右寄りに置くと 540 幅でリアクションが 2 行目に落ちて並びが変わるため。2026-10-10 に撮影で比べて決めた)。押すと設定のログインを開く。直るまで出したまま (閉じるボタンは無い)。接続中の配信には影響しないので、状態の行を error の面にはしない |
| WebSocket サーバーが止まっている (起動に失敗した・途中で止まった) | 同じく足した行に error の色で「WebSocket: 止まっています」を出す。押すと操作パネルを開く。OBS などの外部連携が止まっていることに配信中に気づくため。途中で止まったことは 30 秒ごとに確かめる (03_websocket.md「フロントエンド」) ので、出るまで最大 30 秒かかる |
| 異常が 2 つ以上 | 足した 1 行に並べる。幅に収まらなければその行の中で折り返す |
| ログインの検証に失敗した (ネットワークエラー)・未ログイン | 状態の行には出さない (操作パネルの中だけ)。異常と決まっていない・ログインしないで使う人がいるため |
| 未接続 | 点は控えめな色で「未接続」。流れの場所に接続の入力を出す (上の「未接続で、表示するコメントも無い」) |

## 制約・不変条件（Boundaries）

| 制約 | 理由 |
|------|------|
| 最大同時接続数は32 | メモリとAPI負荷の上限。超過時は接続を拒否する |
| メッセージ重複排除キーは `connection_id:message_id` の複合キー | connection_idなしだと異なる配信間でYouTubeのmessage_idが衝突する可能性がある |
| バックエンドは接続ごとに受け取った message_id を覚え、再び届いたものを捨てる | YouTube は同じ接続に同じメッセージを再送することがある（実測: 同じ id・同じ timestampUsec が約60秒で4回）。フロントの重複排除だけでは、TTS・WebSocket・視聴者の集計に重複が流れる |
| ポーリング間隔は1,500msを下限とし、取得に成功している間は応答の `timeoutMs`（無ければ10,000ms）を上限とする | 1,500msより短くするとAPIブロックのリスクがある。YouTube が応答で指示する間隔より長く待っても、遅れが増えるだけで得るものが無い（ADR-007） |
| プッシュ通知は「取りに行く」合図にだけ使い、メッセージは必ず `get_live_chat` の応答から取る | 通知の中身にメッセージは入っていない。取得の経路を 1 つに保ち、重複排除・初見判定などを通知の有無で変えない（ADR-008） |
| プッシュ通知が働いていなくても、ポーリングで取り続ける | 通知の仕組みは公開の資料が無く、黙って壊れうる。通知が届かないことを理由に取得を止めない（ADR-008） |
| プッシュ通知の受信に Cookie・認証ヘッダーを送らない | 通知はログインなしで受けられる。ログイン情報を送る先を増やさない |
| 初見さん判定は `save_message`（`upsert_viewer_stream`含む）の**後**に実行する | 判定前にDBにデータが存在している必要がある |
| システムメッセージ（`message_type == "system"`）は初見判定の対象外 | システムメッセージはユーザーの発言ではない |
| 配信内コメント数カウンタはメモリ上のHashMapで管理し、DBには保存しない | O(1)のパフォーマンスが必要。再接続時はDBから復元可能 |
| ギフトの handle から channel_id を引くとき、候補が2件以上なら特定しない | 別人に紐付けると読み仮名・初見判定・集計がすべて誤る。特定しないだけなら表示と保存は正しい |
| 特定できないギフトの channel_id は `""` とし、viewer_profiles を作らない | 仮のIDでプロフィールを作ると本物の channel_id と二重になる |
| ジュエル数は本文から読めたときだけ記録し、推測しない | ギフトの価格は YouTube 側で変わりうる |
| リアクションは更新（`emojiFountainDataEntity`）単位で記録し、1秒ごとの時刻を推測で振らない | バケットの時間順が応答から判別できない。推測した時刻は分析結果を誤らせる |
| リアクションの件数は `reactionsData[].reactionCount` だけから数える | `totalReactions` と二重の出どころを持つと、食い違ったときにどちらが正か決められない |

## 未決事項（Open Questions）

「配信中の画面」(2026-10 の作り直し) で、まだ決めていないこと。決まったら「振る舞い」に移す。

| 項目 | 仮の扱い |
|------|------|
| 複数の配信をまとめて接続する手段 | 未設計。コラボで続けて接続するときの手間を減らす案 (シフィさん、2026-10-09)。今は「接続したら操作パネルを隠す」を無効にすれば続けて接続できる |
| スパチャのティアの色の読みやすさ | YouTube の色のまま出す (シフィさん、2026-10-09)。オレンジのティアは白い文字で WCAG AA (4.5:1) に届かないが、承知の上で YouTube に合わせる。設定で読みやすさを調整するオプションは未設計 |
| 主の配信をどれにするか | 最初の接続 (本人の配信とは限らない)。ログイン中のチャンネルと一致する接続を主にする案もあるが、ログインしていない・テストで他の人の配信に接続する場合があるので、今は採らない。視聴者情報 (読み仮名・メモ) の配信者も最初の接続に固定されている。コラボで相手側の視聴者を扱うときの整理が要る |
| 「流れたもの」の欄の 30 秒・1/8・2 件などの値 | 試作での仮の値。配信で使って見直す。欄の高さ (既定 1/8) はドラッグで変えられる |
| コメントのピン留め、視聴者での絞り込み | 未設計 (ブリーフ §4) |
| 参加型の一覧 (参加中・待機) と、パネルの配置の選択 | 未設計。参加の受け付け方も未決 (ブリーフ「機能への影響」) |
| 同時接続数・いいね数 | 取得していない。状態の行には出せるものだけを出す |
| 配信中に使わない操作を隠す設定 | 未設計 (ブリーフ §4) |

## InnerTube API

### エンドポイント

| 用途 | URL |
|------|-----|
| メッセージ取得 | `https://www.youtube.com/youtubei/v1/live_chat/get_live_chat?key={api_key}` |
| アカウントメニュー（認証検証） | `https://www.youtube.com/youtubei/v1/account/account_menu` |

### リクエスト形式

```json
{
    "context": {
        "client": {
            "clientName": "WEB",
            "clientVersion": "{extracted_version}"
        }
    },
    "continuation": "{continuation_token}",
    "invalidationPayloadLastPublishAtUsec": "{最後に受けた通知の発行時刻}"
}
```

`invalidationPayloadLastPublishAtUsec` は、プッシュ通知を 1 件以上受けているときだけ付ける（「プッシュ通知」）。公式のチャット画面と同じ形にする。

### Continuation Token

メッセージ取得の継続に使用するトークン。Protocol Buffer形式でエンコードされている。

| データタイプ | 優先度 | 用途 |
|-------------|-------|------|
| `invalidationContinuationData` | 1 | 新メッセージ検出時に即座に通知 |
| `timedContinuationData` | 2 | 指定時間後にポーリング |
| `reloadContinuationData` | 3 | フォールバック |

採用したデータの `timeoutMs`（ミリ秒）を、次の取得までの待ちの上限に使う（「取得の間隔」）。
`invalidationContinuationData` の `invalidationId.topic`（`chat~{動画ID}`）のプッシュ通知を受け、取得を早める合図に使う（「プッシュ通知」）。

### チャットモード切り替え

#### コマンドレベルの動作

`set_chat_mode` コマンドは `tokio::sync::watch` チャネル経由で監視タスクにモード変更要求を送信する。
InnerTubeClient の所有権は監視タスクに一本化されており、コマンドハンドラからは直接アクセスしない。

```
set_chat_mode(connection_id, mode)
  → StreamConnection.chat_mode_tx.send(mode)  // watch チャネルで送信
  → 監視ループがポーリングのたびに chat_mode_rx の最新値（選ばれたモード）を読む
  → クライアントの現在のモードと違えば client.set_chat_mode(mode) を適用（失敗したら次のポーリングでやり直す）
  → 次のAPIリクエストで新しいcontinuation tokenが使用される
```

> **注意**: モード変更は非同期で適用される。`set_chat_mode` コマンドの戻り値 `true` は「要求受付成功」を意味し、「即時適用完了」ではない。

#### 切り替えの振る舞い

| 状況 | 結果 |
|------|------|
| 「全て」を選んでアプリを再起動する | 前回選んだ「全て」のまま始まる（config.toml の `chat_display.chat_mode`、[09_config.md](09_config.md)） |
| F5 リロード | config.toml の値でボタンの表示を戻す（選択はすべての接続に送るので、接続中のモードと一致する） |
| 接続中に「全て」を選ぶ | 次のポーリングから「全て」で取得する |
| continuation token の書き換えに失敗した（形式が想定外など） | warn ログを出し、次のポーリングで新しい token に対してやり直す。反映されるまで毎回試す |
| 反映前に別のモードを選び直した | 最後に選んだモードだけを反映する |

#### InnerTubeClient内部の切り替え方式

continuation token の中のチャットモードの値を書き換える（Binary Modification）。

**token の形式（実データで確認）:**

| 項目 | 内容 |
|------|------|
| 文字 | URL-safe base64（`-` `_` を使う） |
| パディング | 付くことがあり、`=` はパーセントエンコードされて `%3D` で届く（観測では約26%） |
| 構造 | protobuf。field 119693434（メッセージ）→ field 16（メッセージ）→ field 1（varint）がチャットモード。4 = TopChat、1 = AllChat |

**書き換え:**

1. `%3D` を `=` に戻し、パディングの有無どちらでも URL-safe base64 として読む
2. protobuf として上の経路をたどり、field 1 の値を書き換える（1 と 4 はどちらも1バイトなので長さは変わらない）。それ以外のバイトは変えない
3. URL-safe base64（パディング無し）で書き戻す

| 入力 | 結果 |
|------|------|
| field 16 の field 1 = 4 の token を AllChat に | field 1 だけが 1 になった token |
| 末尾が `%3D` の token | 同じく書き換えられる |
| 経路のどこかが無い・protobuf として読めない | 失敗（None）。token は変えない |
| すでに目的のモード | そのまま成功 |

経路はバイト列の見た目ではなく protobuf の構造でたどる。見た目で探すと、時刻などの別の値の中にある同じバイト列を書き換えてしまう（実データで8件観測）。

## 接続処理フロー

```
1. ユーザーがURLを入力 → connect_to_stream呼び出し
        ↓
2. URLからビデオIDを抽出
        ↓
3. YouTubeページをフェッチ、以下を抽出:
   - API Key
   - Client Version
   - Continuation Token
   - 配信者情報（チャンネルID、名前）
   - チャットモード切替用トークン
        ↓
4. InnerTubeクライアントを初期化
        ↓
5. 新規セッションをDBに作成
        ↓
6. 配信内コメント数カウンタを初期化
   ├─ 同一video_idのセッションがDBに存在する場合 → DBから集計して復元
   └─ 新規の場合 → 空のHashMapで初期化
        ↓
7. チャット監視タスクを起動（tokio::spawn）
        ↓
8. ConnectionResultをフロントエンドに返却
```

### メッセージ復元（未実装）

同一配信への再接続時のメッセージ復元は現在未実装。各接続は新規セッションとして開始される。
配信内コメント数カウンタ（`in_stream_comment_counts`）のみDBから復元される。

## チャット監視タスク

```
┌─ ループ（1.5〜10秒ごと。「取得の間隔」）───────┐
│ 1. CancellationTokenでキャンセル確認          │
│ 2. fetch_chat()でAPI呼び出し                  │
│    ├─ 応答待ちの間も切断を受け付ける           │
│    ├─ 成功 → 連続失敗回数を0に戻す            │
│    ├─ 失敗 → 連続失敗回数を1増やす            │
│    └─ 新しいcontinuation tokenを取得          │
│ 3. chat_mode_rx でモード変更要求を確認         │
│    └─ 変更あり → client.set_chat_mode(mode)  │
│ 4. この接続で受け取り済みの id を捨てる        │
│ 5. 残りを 1 トランザクションで処理（1件ずつ）: │
│    ├─ ギフトなら handle から channel_id を特定  │
│    ├─ 配信内コメント数カウンタ更新              │
│    ├─ DBに保存（save_message）                │
│    │   ├─ INSERT OR IGNORE (messages)         │
│    │   ├─ upsert_viewer_profile               │
│    │   └─ upsert_viewer_stream(video_id)      │
│    └─ is_first_time_viewer(video_id)で初見判定 │
│ 6. 各メッセージを送る:                         │
│    ├─ GuiChatMessageに初見・回数を付与し、     │
│    │   Tauriイベントを発行                    │
│    ├─ WebSocket に配信                        │
│    └─ TTS キューに追加                        │
│ 7. リアクション更新を処理:                     │
│    ├─ 前回以下の update_time_usec なら捨てる   │
│    ├─ DBに保存（reactions）                   │
│    ├─ Tauriイベント chat:reaction を発行       │
│    └─ WebSocket に Reaction を配信            │
│ 8. 次の取得まで待つ（1.5秒から空振りが続くと   │
│    timeoutMs まで延ばす。失敗が続くと延ばし、   │
│    15回続いたら切断して抜ける）                 │
│    └─ プッシュ通知が届いたら待ちを打ち切る          │
│       （前回の取得から 1.5秒は空ける）          │
└───────────────────────────────────────────────┘

┌─ プッシュ通知の受信（接続ごとに 1 本。「プッシュ通知」）┐
│ 通知のサーバーにつなぎ、チャットの更新を待つ     │
│ ├─ 通知が届いた → 監視タスクに合図              │
│ ├─ 受信の接続が閉じられた → 開き直す            │
│ └─ 壊れた → 間を空けて最初からつなぎ直す        │
│ 監視タスクが終わったら一緒に止まる              │
└─────────────────────────────────────────────────┘
```

### 初見さん判定

配信者チャンネルにおいて初めてコメントした視聴者を判定する。

#### データ構造: viewer_streams テーブル

各視聴者がどの配信にコメントしたかを記録する。

```sql
CREATE TABLE viewer_streams (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    viewer_profile_id INTEGER NOT NULL,     -- viewer_profiles.id
    video_id TEXT NOT NULL,                 -- 配信のvideo_id
    first_comment_at TEXT NOT NULL,         -- この配信での最初のコメント時刻
    last_comment_at TEXT NOT NULL,          -- この配信での最新のコメント時刻
    message_count INTEGER DEFAULT 1,        -- この配信でのコメント数
    created_at TEXT DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (viewer_profile_id) REFERENCES viewer_profiles(id) ON DELETE CASCADE,
    UNIQUE(viewer_profile_id, video_id)
);
```

#### 判定方法

`viewer_streams` テーブルで、視聴者の最古の `video_id` が現在の配信の `video_id` と一致するかで判定する。

```
メッセージ受信時:
  1. save_message → upsert_viewer_profile (viewer_profile_id を取得)
                  → upsert_viewer_stream(viewer_profile_id, video_id)
  2. is_first_time_viewer(broadcaster_id, channel_id, video_id) で判定:
     oldest_video_id = SELECT video_id FROM viewer_streams vs
                       JOIN viewer_profiles vp ON vs.viewer_profile_id = vp.id
                       WHERE vp.broadcaster_channel_id = ? AND vp.channel_id = ?
                       ORDER BY vs.first_comment_at ASC LIMIT 1
     msg.is_first_time_viewer = (oldest_video_id == current_video_id)
```

#### 注意事項

| ポイント | 説明 |
|---------|------|
| 配信者スコープ | `viewer_profiles.broadcaster_channel_id` 経由で配信者スコープを維持 |
| 永続性 | `viewer_streams` テーブルに基づくためアプリ再起動後も正確 |
| 配信内一貫性 | DB問い合わせのため、再接続後も自動的に正しい判定を維持（メモリキャッシュ不要） |
| 判定タイミング | `save_message`（`upsert_viewer_stream` 含む）の**後**に判定する |
| システムメッセージ | `message_type == "system"` のメッセージは判定対象外 |
| 特定できないギフト | `channel_id == ""` のギフトは判定対象外（false） |
| メンバーシップギフトの受け取り | 判定対象外（false）。`save_message` は viewer_profiles・viewer_streams を更新しない |
| 将来の拡張 | 視聴者の訪問配信一覧、前回来た配信の特定等に利用可能 |

### 配信内コメント数カウンタ

配信（video_id）単位での視聴者ごとのコメント回数を管理する、メモリ上のカウンタ。

#### データ構造

```rust
/// video_id単位の視聴者コメント数カウンタ
/// key: channel_id, value: コメント回数
type InStreamCommentCounter = HashMap<String, u32>;
```

#### ライフサイクル

| イベント | 動作 |
|---------|------|
| 新規接続 | 空のHashMapを作成 |
| 再接続（同一video_id） | DBから該当セッションのメッセージを集計し、channel_idごとのカウントで初期化。URL の書き方（`watch?v=`・`/live/`・`youtu.be/`）が前回と違っても同じ配信として数える |
| メッセージ受信 | カウンタをインクリメントし、現在値を `in_stream_comment_count` に設定。システムメッセージ・視聴者を特定できないギフト・メンバーシップギフトの受け取りは数えない（`None`） |
| 切断 | カウンタを破棄（DBにメッセージが保存されているため復元可能） |

#### 再接続時の復元SQL

```sql
SELECT m.channel_id, COUNT(*) as count
FROM messages m
JOIN sessions s ON m.session_id = s.id
WHERE s.video_id = {video_id}
  AND m.message_type NOT IN ('system', 'membership_gift_redemption')
  AND m.channel_id <> ''
GROUP BY m.channel_id
```

#### パフォーマンス

| 操作 | 計算量 |
|------|--------|
| カウント参照 | O(1) - HashMap lookup |
| カウント更新 | O(1) - HashMap insert/update |
| 初期化（再接続時） | O(N) - Nはユニーク視聴者数 |

### 受信済み message_id の記憶

接続ごとに、受け取った message_id を直近 10,000 件まで覚える。超えたら古いものから忘れる。
YouTube の再送は数十秒〜数分のうちに届くので、直近だけ覚えれば足りる。件数に上限を設けて、長時間の配信でもメモリを一定に保つ（接続あたり約1MB）。

| 状況（上限を3件とした例） | 結果 |
|------|------|
| A, B, A の順に届く | A, B を処理し、2回目の A を捨てる |
| A, B, C, D, A の順に届く | A, B, C, D を処理する。D を覚えた時点で A を忘れているので、最後の A も処理する |
| message_id が空のメッセージ | 重複の判定をせず、常に処理する（空の id 同士を同じものとみなさない） |
| 切断 | 記憶を破棄する。再接続は新しい接続なので、YouTube が返す直近のコメントも新着として扱う |

### 取得の間隔

コメントが続いている間は短い間隔で取り、途切れたら少しずつ延ばして取得の回数を減らす。
延ばすのは YouTube が応答で指示する間隔（`timeoutMs`）までで、それより長くは待たない（ADR-007）。

**空振り**: 取得に成功し、新しいメッセージが 0 件だったこと。再送として捨てたメッセージは数えない。
リアクションの更新だけが届いたときも空振りに数える（読み上げや一覧の速さに関わるのはメッセージのため）。

| 連続空振り回数 | 次の取得までの待ち |
|------|------|
| 0（新しいメッセージが届いた） | 1.5秒 |
| 1 | 1.5秒 |
| 2 | 2.5秒 |
| 3 | 3.5秒 |
| n（2以上） | 1.5 + (n − 1) 秒。上限を超えるときは上限 |

上限は、その応答で採用した continuation の `timeoutMs`。応答に `timeoutMs` が無ければ 10秒。
上限が 1.5秒より短いときは 1.5秒で取る（下限を優先する）。

| 例 | 次の取得までの待ち |
|------|------|
| `timeoutMs` 10000 の応答で空振りが続く | 1.5 → 1.5 → 2.5 → 3.5 → … → 9.5 → 10 → 10 …（10回目から 10秒） |
| 空振り6回（待ち 6.5秒）のあと新しいメッセージが届く | 1.5秒 |
| `timeoutMs` 3000 の応答で空振りが続く | 1.5 → 1.5 → 2.5 → 3 → 3 … |
| `timeoutMs` 1000 の応答 | 空振りの回数によらず 1.5秒 |
| `timeoutMs` が無い応答（`reloadContinuationData` など）で空振り12回 | 10秒 |
| 空振り5回 → 取得に失敗 → 成功して新しいメッセージ 0 件 | 失敗の後は 1.5秒（「取得に失敗したとき」）。次の空振りは6回目として数え、待ちは 6.5秒 |
| 接続が2つある | 接続ごとに別々に数える |

- 静かな状態から最初に届くコメントは、最大で上限の秒数（`timeoutMs` 10000 なら 10秒）遅れて取れる。コメントが続いている間は最大 1.5秒。
  プッシュ通知が働いている間は、静かな状態からでも通知の直後（前回の取得から 1.5秒以上たっていれば）に取れる（「プッシュ通知」）
- 待っている間も切断を受け付ける（今までどおり）

### 取得に失敗したとき

YouTube 側の一時的な不調ならそのまま続け、復旧しそうにないときは自動で切断して知らせる。
接続しているつもりで何も取れていない状態を放置しない。

失敗として数えるもの: リクエストのタイムアウト（全体15秒・接続5秒）、ネットワークエラー、成功（2xx）以外の HTTP ステータス、JSON として読めない応答。
応答が返ってきてメッセージが 0 件なのは失敗ではない。

| 連続失敗回数 | 次の取得までの待ち |
|------|------|
| 0（成功） | 「取得の間隔」に従う（1.5〜10秒） |
| 1〜10 | 1.5秒 |
| 11 | 3秒 |
| 12 | 6秒 |
| 13 | 12秒 |
| 14 | 24秒 |
| 15 | 待たずに切断する |

- 1 回でも成功したら連続失敗回数は 0 に戻る（例: 失敗12回 → 成功 → 失敗 なら、次の待ちは 1.5秒）
- 失敗は空振りに数えず、連続空振り回数も変えない（「取得の間隔」）
- 15回目で切断するとき: セッションを閉じ、接続を一覧から消し、エラー「チャットの取得に15回続けて失敗したため切断しました」を表示する（「接続状態遷移」の監視タスク終了と同じ経路）
- 1〜10回目の待ちを今までと同じにするのは、短い不調（数秒〜15秒）で取りこぼす時間を増やさないため

### プッシュ通知

YouTube はチャットが更新されると、通知のサーバー（signaler）から購読者に知らせる。公式のチャット画面はこれを受けて取りに行く。
liscov も通知を受け、届いたら「取得の間隔」の待ちを打ち切って取りに行く。静かな状態から最初に届くコメントの遅れ（最大 `timeoutMs`、今は 10秒）を、1.5秒以内に縮めるのが目的（ADR-008）。

通知は取りに行く合図にだけ使う。メッセージは今までどおり `get_live_chat` で取り、ポーリング（「取得の間隔」「取得に失敗したとき」）も止めずに動かし続ける。
通知が使えないとき・壊れたときは、ポーリングだけで今までどおり取れる。実験的な機能で、設定 `chat_fetch.push_notification`（既定 `true`、09_config.md）で止められる。
配信中に通知が原因の問題が起きたとき、配信を止めずに回避できるよう、設定の画面から切り替えられ、すぐ効く。

#### 受け始めと終わり

| 状況 | 動作 |
|------|------|
| 接続が成立した（設定が有効） | その接続の通知を受け始める。接続ごとに 1 本 |
| 設定が無効 | 通知を受けない。`invalidationPayloadLastPublishAtUsec` も付けない |
| 接続中に設定を無効にした | すべての接続の通知の受信をすぐ止める。取得はポーリングで続く（再接続は不要） |
| 接続中に設定を有効にした | すべての接続で通知を受け始める（再接続は不要） |
| 視聴ページに通知の API キー（後述）が無い | 通知を使わず、ポーリングだけで取る（info ログ） |
| 切断した・監視タスクが終わった | 通知の受信も止める |
| チャットモードを切り替えた | 受信はそのまま（通知は動画単位で、モードによらない） |

#### 設定の画面

設定の画面に「チャット取得」のタブを足す（「YouTube認証」の次）。中身はチェック 1 つ。

| 要素 | 内容 |
|------|------|
| チェック | 「プッシュ通知でコメントを早く取る（実験的）」。`chat_fetch.push_notification` と同じ。押すとすぐ保存し、すぐ効く |
| 説明 | 「YouTube からの通知を受けて、静かなときの最初のコメントを早く取ります。コメントの取得がおかしいときはオフにしてください。オフでも今までどおり取得します。」 |
| 保存に失敗した | エラーを出し、チェックを保存されている値に戻す |

#### 通知が届いたとき

| 状況 | 次の取得 |
|------|------|
| 待っている間に通知が届き、前回の取得を始めてから 1.5秒以上たっている | すぐ取る |
| 待っている間に通知が届き、前回の取得を始めてから 1.5秒たっていない | 前回の取得を始めてから 1.5秒で取る |
| 取得の応答を待っている間に通知が届いた | その取得の後の待ちを 1.5秒にする（通知が指す更新を、その取得が含んでいないことがあるため） |
| 待っている間に通知が何件届いても | 取得は 1 回。次の待ちに持ち越さない |
| 通知で取りに行き、新しいメッセージが 0 件 | 空振りに数える（「取得の間隔」は変えない） |
| 取得に 11 回以上続けて失敗し、待ちを延ばしている間に通知が届いた | 待ちを打ち切らない（「取得に失敗したとき」の延長を優先する。通知で失敗の間隔が縮むと、延ばす意味がなくなるため） |

| 例 | 次の取得 |
|------|------|
| 空振りが続いて待ち 9.5秒。前回の取得から 4秒で通知 | 通知の直後 |
| 前回の取得から 0.5秒で通知 | その 1秒後（前回から 1.5秒） |
| 待ち 6.5秒の間に通知が 3 件 | 最初の通知の直後に 1 回。その後の待ちは取得の結果で決まる |
| 取得の応答待ちの間に通知。取得の結果は空振り 5 回目（本来の待ち 5.5秒） | 1.5秒後 |

- 取得のリクエストには、最後に受けた通知の発行時刻を `invalidationPayloadLastPublishAtUsec` として付ける（「リクエスト形式」）
- 前回の取得から 1.5秒空けるのは、ポーリング間隔の下限（「制約・不変条件」）を通知のときも守るため。公式のチャット画面は通知の直後に取るが、liscov はそれより短くしない

#### 壊れたと判断する条件とつなぎ直し

| 状況 | 動作 |
|------|------|
| 受信の接続をサーバーが閉じた（約 4 分ごとに起きる） | 同じ通知のセッションのまま、すぐ開き直す。壊れたとはみなさない |
| 受信の接続で 60秒何も届かない（通知・20秒ごとの定期のメッセージ・`noop` のいずれも） | 壊れたとみなす |
| 通知の手順で失敗した（タイムアウト・ネットワークエラー・成功以外の HTTP ステータス・読めない応答・サーバーからの `close`・エラーの応答） | 壊れたとみなす |
| 壊れた | ポーリングだけで取り続ける。30秒後に最初からつなぎ直す（warn ログ） |
| つなぎ直しに続けて失敗した | 待ちを倍に延ばす（30 → 60 → 120 → 240 → 300 → 300 …秒）。上限 5分。諦めない |
| つなぎ直して通知を受けられた（購読の開始が届いた） | 次につなぎ直すときの待ちを 30秒に戻す（info ログ） |

- 画面には何も出さない。通知が壊れても取得は続いていて、遅れが今の最大 10秒に戻るだけのため。状態はログで追う

#### 通知のサーバーとのやりとり

公開の資料は無い。公式のチャット画面の通信を観察して合わせた（2026-10、ADR-008）。

| 手順 | 内容 |
|------|------|
| API キー | 視聴ページの HTML の `ytcfg` の `LIVE_CHAT_BASE_TANGO_CONFIG.apiKey`。InnerTube の API キーとは別 |
| 共通のヘッダー | `Origin: https://www.youtube.com`、`Referer: https://www.youtube.com/`。無いと 403 になる |
| 1. サーバーを選ぶ | `POST https://signaler-pa.youtube.com/punctual/v1/chooseServer?key={キー}`（`Content-Type: application/json+protobuf`）。応答の先頭が gsessionid |
| 2. チャンネルを開く | `POST .../punctual/multi-watch/channel?VER=8&gsessionid=..&key=..&RID={乱数}&CVER=22&zx={乱数}&t=1`。本文で `chat~{動画ID}` を購読する。応答の `["c", SID, ...]` が SID |
| 3. 受信 | `GET .../punctual/multi-watch/channel?VER=8&gsessionid=..&key=..&RID=rpc&SID=..&AID={最後に受けた番号}&CI=0&TYPE=xmlhttp&zx=..&t=1`。開いたまま「長さ + 改行 + JSON」が続く。約 4 分でサーバーが閉じる |
| 4. 資格の更新 | 約 4 分ごとに `POST .../punctual/v1/refreshCreds?key=..&gsessionid=..`。本文は受信の最初に届くトークン。10 分の実験では無くても通知は続いたが、公式のチャット画面に合わせて送る |

受信で届くもの:

| 中身 | 意味 | 扱い |
|------|------|------|
| `[[null,null,["{トークン}"]]]`（最初） | 資格の更新に使うトークン | 覚える |
| `[[[["1",[["{時刻}"]]]]]]` | 購読の開始 | つながった |
| `[[[["1",[null,[[[null,"{版}","{発行時刻}",...]]]]]]]]` | チャットが更新された | 通知。発行時刻を覚えて合図する |
| `[[[["1",[null,null,["{時刻}"]]]]]]` | 20秒ごとの定期のメッセージ | 通知ではない。生きている印 |
| `["noop"]` | 何も無いときの生きている印（30秒ごと） | 生きている印 |
| `["close"]`・`{"__sm__": ...}` | 閉じる・エラー | 壊れた |

### 状態の行の統計（StatusLine）

状態の行の左に、画面のメッセージ一覧の統計を出す。未接続のときは出さない（点と「未接続」だけ）。

| 表示 | 値 |
|-----|-----|
| 件 | 画面のメッセージ一覧の件数（「コメントを消す」で 0）。まとめた受け取りは数えない |
| /分 | 直近 60 秒に投稿されたコメントの数（投稿時刻 `timestamp_usec` で数える）。コメントが止まれば下がっていく（5 秒ごとに数え直す） |
| 人 | 画面のメッセージ一覧にいる視聴者の数（`channel_id` ごと。視聴者を特定できないギフトは数えない） |

| 状況（/分、いま 12:00:00） | 結果 |
|------|------|
| 11:58:00・11:59:10・11:59:50 に投稿されたコメント | 2 |
| 最後のコメントが 11:59:50 で、そのあと 60 秒コメントが無い | 12:01:00 までに 0 になる |
| アーカイブ（投稿時刻が過去）のコメントだけ | 0 |

| 状況（人） | 結果 |
|------|------|
| UCa が 3 件、UCb が 1 件、視聴者を特定できないギフトが 1 件 | 2 |
| UCa のメンバーシップギフト 1 件と、それにまとめた UCb・UCc の受け取り | 3（件は 1） |

件・人はストアが受信のたびに差分で数える（全件を数え直さない）。/分は一覧の末尾から辿り、投稿時刻が 90 秒より前のメッセージに当たったら止める
（一覧は到着順。複数の接続で到着が前後しても数十秒に収まる前提）。

**表示中の件数:** フィルタ・表示件数で一部を隠しているときだけ出す。

| 状況 | 結果 |
|------|------|
| フィルタも表示件数も使っていない | 出さない |
| 全 800 件で、表示件数を 500 にした | `表示中 500 / 全 800 件` |
| 全 30 件で、表示件数 500 | 出さない (隠しているものが無い) |
| 全 80 件で、検索で 12 件に絞った | `表示中 12 / 全 80 件` |

### フロントエンド状態の復元（F5リロード後）

ページリロード時にバックエンドのアクティブ接続をフロントエンドに復元する。

| 項目 | 詳細 |
|------|------|
| メソッド | `chatStore.restoreConnections()` |
| 呼び出しタイミング | `+page.svelte` の `onMount` で `setupEventListeners()` の後に実行 |
| 実行内容 | `get_connections` コマンドで全接続情報を取得し、`FrontendConnectionState` に変換してMapに追加。各接続の `get_connection_reactions` でリアクションの累計を復元する（失敗したらその接続の累計は 0 から始める） |
| 復元後の動作 | バックエンドの監視ループは継続しているため、復元後は新着メッセージが正常に受信される |
| 失敗時 | `console.warn` でログ出力、アプリは正常に動作（接続リストが空のまま） |

### 接続状態遷移（個別接続単位）

```
  開始                                    切断
(なし) → Connecting → Connected → Disconnecting → (削除)
                           │
                           ├─ (取得に15回続けて失敗) → (削除 + エラー通知)
                           └─ (監視タスク異常終了) → (削除 + エラー通知)

Connecting → (接続失敗) → (削除 + エラー通知)
```

多接続モデルでは各接続が独立した状態を持つ。グローバルな `paused` 状態は存在しない。

| 状態 | 説明 | UI表示 |
|-----|------|-------|
| `connecting` | 接続処理中（API応答待ち） | 「接続」を無効にし「接続中…」と出す。札の点は控えめな色。その接続の切断ボタンは無効 |
| `connected` | 接続済み、メッセージ受信中 | 札の点は success の色。操作パネルの接続の一覧に出す |
| `disconnecting` | 切断処理中 | 札の点は控えめな色 |

### スクロール動作

#### 自動スクロール

振る舞いは「配信中の画面」の「自動スクロール」が正。ここは実装の詳細。

| 項目 | 実装 |
|-----|-----|
| 状態 | `src/lib/utils/auto-return.ts` の `AutoReturnState`。「最新を追っている」「離れていて、期限 (時刻) に戻る」「離れていて、戻らない (期限 `null`。視聴者情報パネルで打っている間)」のどれか。遷移は純粋関数 (`leaveLatest`・`activity`・`reachLatest`・`tick`・`hold`・`release`) で、`ChatDisplay.svelte` が呼ぶ |
| 戻るまでの時間 | `AUTO_RETURN_MS` = 30 秒 |
| 追うとき | 新着で `queueMicrotask` から virtua の `scrollToIndex(最後, { align: 'end' })`。流れの高さが変わったときも追っていれば合わせ直す |
| 手でのスクロールの判定 | 流れの上の `wheel`・`pointerdown`・`keydown`・`touchstart` から 1 秒以内のスクロールだけを手でのスクロールとみなす。virtua が行の高さを測り直すときのスクロールでは止めない (たくさん届いても追うのをやめない)。手で離れたら `scrollBy(0)` で virtua の合わせ直し (`scrollToIndex` は行の高さが測れるまで目標へ合わせ直し続ける) を今の位置に置き換え、最新へ引き戻されないようにする |
| 最新にいるかの判定 | `getScrollOffset() + getViewportSize() >= getScrollSize() - 4px`。最新にいるとき (手でもプログラムでも) は追うのを再開する |
| 流れの上の操作 | `pointermove`・`click` で期限を延ばす (`activity`) |
| 期限の確認 | 離れている間だけ 1 秒ごとに `tick` |
| 視聴者情報のパネルから過去のコメントへ移ったとき | `leaveLatest` (手で離れたのと同じ扱い) |
| 離れている間に届いた優先順位 1・2 | 離れたときの一覧の最後のもの (`awaySince`) より後の、表示中の一覧の優先順位 1・2 を `src/lib/design/flow.ts` の `arrivedSince` で数える (流れたものの欄と同じ判定)。`awaySince` が表示件数で外れたら、一覧のすべてが離れた後のもの |
| 表示するコメントが無くなったとき (クリア・再接続) | 追う状態に戻す (離れる先が無いため) |

### タイムゾーン変換

タイムスタンプはバックエンドでUTCとして保存され、フロントエンドでユーザーのローカルタイムゾーンに変換して表示される。

#### データフロー

```
YouTube API (timestampUsec: マイクロ秒)
    ↓ Backend: chrono::DateTime::from_timestamp()
UTC DateTime (RFC3339形式)
    ↓ Frontend: new Date() + toLocaleTimeString()
ローカルタイムゾーン (HH:MM:SS形式)
```

#### 変換仕様

| レイヤー | 形式 | 例（JST +09:00の場合） |
|---------|------|----------------------|
| YouTube API | マイクロ秒 | `1737020127000000` |
| Backend保存 | RFC3339 (UTC) | `2025-01-16T04:55:27+00:00` |
| Frontend表示 | HH:MM:SS (ローカル) | `13:55:27` |

#### 実装詳細

**Backend (Rust):**
```rust
fn format_timestamp(timestamp_usec: &str) -> String {
    let secs = usec / 1_000_000;
    let datetime = chrono::DateTime::from_timestamp(secs, 0);
    datetime.to_rfc3339()  // UTC RFC3339形式
}
```

**Frontend (TypeScript):**
```typescript
const date = new Date(message.timestamp);  // RFC3339をパース
date.toLocaleTimeString('ja-JP', {         // ローカルタイムゾーンに変換
    hour: '2-digit',
    minute: '2-digit',
    second: '2-digit'
});
```

#### 注意事項

- データベースにはUTCで保存（国際標準に準拠）
- 表示はユーザーのシステム設定に基づくタイムゾーンで変換
- `timestamp_usec`フィールドは元のマイクロ秒精度を保持（必要に応じて使用可能）

#### 表示件数制限

表示件数の制限は、性能の低い PC で CPU・メモリの負荷を下げるためのもの ([brief.md](../design/brief.md) §5)。
その目的に足りる 2 つだけにする (2026-10-10 に 50・100・200 を外した)。

| オプション | 説明 |
|-----------|------|
| 無制限 | デフォルト |
| 500件 | 負荷を下げる |

| 状況 | 結果 |
|------|------|
| 起動した | 無制限 (表示件数は保存しない) |
| 500件を選び、全 800 件 | 新しい 500 件を出す。状態の行に `表示中 500 / 全 800 件` |

※上限を設定した場合、超過した古いメッセージはアーカイブに移動

#### 実装詳細

- `displayedMessages` = `filteredMessages.slice(-displayLimit)`（displayLimitがnullの場合はfilteredMessagesと同一）
- `filteredMessages` はフィルタのみ適用（ステータスバーの件数表示に使用）
- `messages` は追記と「クリア」だけで変わる（`$state.raw`。足すときは配列ごと差し替え、メッセージ自体は変えない）。
  `filteredMessages` はフィルタが変わらない間、新しく届いた分だけを判定して前回の結果に足す（全件を判定し直すのはフィルタを変えたときと「クリア」のあと）
- アーカイブ = `messages` 配列内に存在するが `displayedMessages` に含まれないメッセージ
- ViewerInfoPanelの過去コメントは `messages` 配列（全件）を参照するため、アーカイブ済みメッセージも表示可能

#### フロントエンドメッセージ上限

フロントエンド（`messages` 配列）に保持するメッセージの件数に上限はない。仮想スクロールにより、大量メッセージでもDOMにはビューポート近辺のみレンダリングされるため、パフォーマンスへの影響は限定的。

#### 仮想スクロール

チャットメッセージの表示にはライブラリ `virtua` による仮想スクロールを使用する。
DOMにはビューポート近辺のメッセージのみレンダリングされ、大量メッセージ（1万件以上）でもスムーズにスクロール可能。

## 視聴者情報パネル

振る舞いは「配信中の画面」の「視聴者の読み仮名・メモ (視聴者情報パネル)」が正。ここは実装の詳細。
押したコメントの行のすぐ下に広げる (2026-10-09 に右からのスライドインから変えた。試作は `src/routes/design-proto/viewer` の C)。

### どの配信者のもとで開くか

視聴者のプロフィールと読み仮名・メモは配信者ごとにある（06_viewer.md「配信者スコープ」）。パネルは、一覧でクリックしたコメントが届いた接続の配信者のもとで視聴者を引き、保存もそこに書く。TTS もメッセージが届いた接続の配信者のもとで読み仮名を引くので、パネルで保存した読み仮名はその接続のコメントの読み上げに使われる。

例: 接続1（配信者A: UCaaa）と接続2（配信者B: UCbbb）に同時に接続している。

| 状況 | 結果 |
|------|------|
| 接続2 に届いた視聴者X（UCxxx）のコメントをクリック | B のもとで X を引く。保存すると B のもとの X に書く（接続2 に X のコメントが届いたら、TTS はこの読み仮名で読む） |
| 接続1 に届いた X のコメントをクリック | A のもとで X を引く |
| パネルを開いたまま、一覧で別の接続に届いたコメントをクリック | クリックしたコメントの接続の配信者で引き直す |
| パネルの「投稿されたコメント」で、別の接続に届いた X のコメントを押す | 一覧のそのコメントへスクロールするだけ。配信者は開いたときのまま |
| パネルを開いたあとでその接続を切断した | 開いたときの配信者のまま。保存もそこに書く |
| クリックしたコメントの接続が切断済み（接続一覧に無い） | パネルを開かない（どの配信者のもとか分からない） |
| クリックしたコメントの接続の配信者 channel_id が分からない | パネルを開かない |

| 空文字の扱い | Noneとして保存（読み仮名なし） |
| 開いてから読み込みが終わるまで | 読み仮名・メモの欄と保存ボタンは押せない（読み込み結果が入力中の内容を上書きしないように） |
| 読み込み中に別の視聴者を開いた | 前の視聴者の読み込み結果は捨てる。フォームの内容と保存先は、いま開いている視聴者のもの（例: A を開いてすぐ B を開き、A の応答があとから届いても、読み仮名は B のまま。保存すると B に書く） |
| 保存の知らせ | パネルは閉じるので、`ChatDisplay` の読み上げ用の領域 (`aria-live="polite"`) に「保存しました」を 3 秒出す。画面では行の名前の横の読み仮名が保存の印 |

**保存フロー:**
```
1. 読み仮名・メモを入力
2. Enter (または「保存」)
3. viewer_upsert_custom_info (存在すれば更新、なければ新規作成)
4. chatStore.setViewerInfo で画面の同じ視聴者の行に読み仮名とメモを出す
5. onSaved → ChatDisplay がパネルを閉じ、「保存しました」を読み上げ用に知らせる
```

### 打っている間と自動スクロール

| 項目 | 実装 |
|-----|------|
| 打っているか | パネルの中にフォーカスがある (`focusin`・`focusout`) か、読み込んだ値から変えた (保存していない変更がある)。変わるたびに `onBusyChange` |
| 打っている間 | `ChatDisplay` が `hold` (戻る期限を無くす。追っている間は何もしない)。打ち終えたら `release` (そこから 30 秒) |
| 開いたとき | `leaveLatest`。押したときの入力の記録を消す (`scrollToIndex` を手でのスクロールとして打ち消さないため) |
| 下端に着いたとき | パネルを開いている間は、手で最新までスクロールしたときだけ追うのを再開する (最新のコメントの下に広げると下端に着くが、それで追いはじめるとパネルが流れていく) |
| パネルの中での入力・クリック | 手でのスクロールに数えない (`data-viewer-panel` の中の `keydown`・`pointerdown` などは記録しない) |
| 閉じたとき | 開く前に最新を追っていたら (`wasFollowing`) `goLatest`。押した行に `focus({ preventScroll: true })` で戻す |
| 30 秒で最新に戻ったとき | パネルを閉じる |
| 広げた行が一覧から無くなったとき | パネルを閉じる |

### 過去コメント表示 (この人のコメント)

当該視聴者のコメントを新着順で表示。
パネルを開いている間に届いたその視聴者のコメントも、そのまま一覧に加わる。

**対象範囲:**
- 現在のプロセスで接続した配信のコメント（フロントエンドの `messages` 配列に存在するもの。`chatStore.getMessagesForChannel`）

**コメントクリック時の挙動:**

| 処理 | 詳細 |
|-----|------|
| 最新から離れる | `leaveLatest` (打っている間は戻らないまま) |
| スクロール | `vlist.scrollToIndex(位置, { align: 'center' })` |
| 強調 | 流れのその行を選択の強調 (`outline-accent`、2px) にし、3 秒で消す |
| パネル | 元の行の下のまま (`keepMounted` で画面の外でも残る)。押したコメントを「この人のコメント」の中で印を付ける |

**エッジケース:**

| ケース | 動作 |
|-------|------|
| メッセージが表示件数で外れた・フィルターで非表示 | 流れに無いのでスクロールしない |
| メッセージが表示範囲内 | 正常にスクロール＆強調 |

### インタラクション

| 操作 | 実装 |
|-----|------|
| 開く | 行の `onClick` → `ChatDisplay.svelte` の `handleMessageClick(message, from)`。`from` は押した行がある所 (`flow`・`flowed`・`thanks`)。流れにそのコメントがあれば流れに広げる |

## エラーハンドリング

### 接続エラー

| エラー | 発生条件 | 動作 |
|-------|---------|------|
| Invalid URL | URLからビデオIDを抽出できない | 接続失敗を返却 |
| Page Fetch Failed | YouTubeページの取得に失敗 | 接続失敗を返却 |
| API Key Not Found | HTMLからAPI Keyを抽出できない | 接続失敗を返却 |
| Continuation Not Found | Continuation Tokenを抽出できない | 接続失敗を返却 |
| Member Only | メンバー限定配信で認証なし | 接続失敗を返却 |

### ポーリングエラー

| エラー | 動作 |
|-------|------|
| API応答エラー（2xx 以外・JSON でない） | warnログ、次のポーリングで再試行（「取得に失敗したとき」） |
| DB保存エラー | warnログ、メッセージ処理は継続 |
| ネットワークエラー・タイムアウト | warnログ、次のポーリングで再試行（「取得に失敗したとき」） |
| 15回続けて失敗 | 切断し、エラーを表示 |

### HTMLパース失敗時のデバッグ

重要な情報が抽出できなかった場合、HTMLを一時ファイルに保存する。

```
%TEMP%/liscov_debug_html_{reason}.txt
```
