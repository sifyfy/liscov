# デザインブリーフ: liscov

更新: 2026-10-08 (合意: 2026-10-08。§1 の手と場面、§2 の優先順位 1 の 2 つの役割とコラボ、§4 の操作の原則、参加型は 2026-10-08 の★4 の途中で追記)

画面のデザインを決めるときの前提。トークン・画面の構成・見た目の判断は、ここに書いたことから理由を引く。
書き方は Claude Code のスキル `app-ui-design` のテンプレートに従う。

## 1. 利用者と状況

- **誰が**: YouTube でライブ配信をしている配信者本人 (VTuber を含む)
- **どこから見るか**: 配信中、メインの画面 (ゲーム・配信ソフト) とは別の位置に置いた小さいウィンドウを、横目で見る。
  配信中は配信ソフト・ゲーム・音声関係など多くのソフトを同時に開いていて、コメントビューアーに割ける面積は小さい。
  4K のディスプレイを 2 枚使う環境でも、liscov のウィンドウは幅 800px・高さ 1090px 程度。
  FHD・WQHD の環境では、同じ見た目の大きさでもっと少ない px になる
- **1 回に見る時間**: 1 秒前後。ゲームや会話の合間にちらっと見る
- **同時にしていること**: ゲームの操作、話すこと、配信の進行。注意はほとんど残っていない。
  コメントの勢いがそれほどなくても、すぐには反応できないことがある
- **手**: ゲーム配信中はコントローラーを握っていて、liscov を**ほとんど操作できない**。操作できるのは、ロード中・雑談の合間と、配信の前後。
  雑談配信では操作できるが、操作ゼロに近いほど、配信者は他の演出に操作の時間を回せる
- **耳**: 読み上げ (棒読みちゃん・VOICEVOX) でコメントを耳で拾うこともある。見ることを補うもので、置き換えるものではない

### 場面

| 場面 | すること | 操作 |
|---|---|---|
| 通常の配信中 | ちらっと見て、スパチャ等・新規さん・コメントの流れを把握し、反応する | ほぼできない |
| コラボの参加型の管理 | 配信者 2 人 + 視聴者の参加型 (Apex など)。管理する側の配信者が、**2 つの配信のコメント欄**を同時に見て参加希望者を管理する。参加中の人と参加を待っている人の一覧が要る | ほぼできない |
| 配信の最後のお礼 | その配信でスパチャ等をくれた人の名前を、まとめて呼んでお礼を言う。その間も最新のコメントの状況が見える必要がある | マウスで操作できる |
| 配信の準備・配信の後 | 接続、視聴者の読み仮名・メモの登録・整理、設定 | できる |

- コラボで他の配信者のコメント欄を見る必要があるのは、知られている限り 2 人のコラボ (2026-10-08、シフィさん)

## 2. 画面ごとの読み取る情報の優先順位

### チャット (配信中に見る画面)

1. 新しく来たスーパーチャット・スーパーステッカー・ギフト・メンバーシップ (ギフトを含む)・マイルストーン
2. 新規さん (そのチャンネルで初めてコメントした人) の初回コメント
3. 新規さんの、その配信での 2 回目以降のコメント
4. 常連の、その配信での初回コメント
5. 常連の、その配信での 2 回目以降のコメント ← **ここが強調の標準**
6. 同時接続数・いいね数・チャット率
7. リアクションが上がっているか、その勢い
8. 総コメント数・コメントした人数

- 強調の段階: 5 (通常のコメント) を標準の見た目とし、1〜4 は標準より強く (1 がいちばん強い)、6〜8 は標準より控えめに見せる
- **優先順位 1 には 2 つの役割がある**:
  - 配信中: 新しく来たものに気づき、流れても見落とさない
  - 配信の最後: その配信のスパチャ等を、**時刻順の一覧**で漏れなく読み上げられる。だから「時間で消える」表し方は合わない。
    新しいものを目立たせ、古いものを控えめにしても、配信全体のものは消さずに残す
- **優先順位 2 (新規さんの初回) は、優先順位 1 とは別の枠**で扱う。タイムリーな反応が大事なので、来たときにすぐ気づけることを優先する
- **2 つの配信を同時に見ているとき**は、どの配信から来たコメントかを、すべての行で見分けられる (色だけに頼らない。540px の幅でも読める)
  - 相手の配信に来たコメント・新規さんは、自分の配信のものと**同じ強さ**で出す。見分けは強さ以外の方法 (印・ラベルなど) で行う
  - ただし相手の配信に来たスパチャ等は、基本的にお礼を言う対象ではない。来たことが分かればよく、**通常のコメントとほぼ同じ強さ**でよい。
    お礼の一覧にも入れない (関係によっては代わりにお礼を言うこともあるので、来たことは分かるようにする)
- 見落としても困らないもの: 接続の設定、表示の設定
- 状況として常に分かっていたいもの: 接続が切れていないか、認証が切れていないか、外部連携 (WebSocket) が止まっていないか。
  いずれも**異常のときだけ**目立てばよい

### 視聴者の補足情報 (準備)

- 読み仮名・メモの登録は、配信中にその場で、または配信後に行う。普段は頻繁に使わないが、必要なときにすぐ使えること
- 登録した情報は、コメント行の名前の横か直下に、小さく補足として出る

## 3. 面積と密度の目標

### 想定する置き方と大きさ

大きさは CSS の px (Windows の表示スケールを掛ける前)。よくある画面の CSS px は、FHD (100%)・4K (200%) が 1920×1080、
WQHD (125%) が 2048×1152、WQHD (100%)・4K (150%) が 2560×1440。

| 置き方 | 幅 × 高さ |
|---|---|
| 縦置きのディスプレイに全画面 | 1080〜1440 × 1920〜2560 |
| 縦置きのディスプレイの上半分 | 1080〜1440 × 960〜1280 |
| 縦置きのディスプレイの 4 分の 1 (四隅に寄せる) | 540〜720 × 960〜1280 |
| 横置きのディスプレイの横 3 分の 1 | 640〜853 × 1080〜1440 |
| 横置きのディスプレイの横 2 分の 1 | 960〜1280 × 1080〜1440 |
| 任意の場所にフローティング | 上の範囲の中 |

- **幅は 540〜1440px、高さは 960px 以上**。高さには余裕があり、幅のほうが厳しい
- **設計の基準にする大きさ**: 540×960 (いちばん小さい)、640×1080 (いちばんよく使われる想定)、960×1080 (広め)。
  1440px 幅の見栄えは優先しない (§5)

### 密度

- 配信中、固定の UI (状態・操作) が占める高さは、ウィンドウの高さの 15% 以下
- 640×1080 で、新しく来た優先順位 1・2 のものと、直近のコメントが 20 件以上見える
- 現状 (2026-10-08): 640×800 で固定の UI が約 4 割、コメントは約 6 件。
  最小幅が 800px (`tauri.conf.json` の `minWidth`) なので、FHD の横 3 分の 1 や縦の 4 分の 1 には収まらない

## 4. 準備・操作のフロー

### 操作の原則

- **配信中の目的 (§2 の優先順位 1〜8 の把握と、状態の把握) は、操作ゼロで達成できる**
- 大事な情報を、クリックやマウスを載せる操作の奥に置かない。「押して片付ける」「開いて見る」を前提にしない
  (押せば早く片付く、のような補助としてはあってよい)
- 自動スクロールが止まったままにならない。合間にスクロールして戻し忘れても、しばらく操作が無ければ最新に戻る
- 操作は、合間や配信の前後に、マウスで 1〜2 手で済む

### 作業ごとの目標

| 作業 | 目標 |
|---|---|
| 問題が起きたときに、配信への接続をやり直す | 2 手以内。ただし配信中は目立たせない |
| 特定のコメントを、流れても常に見える状態にしておく | コメントから 1〜2 手。スクロールを止めて戻す必要が無い |
| 特定の視聴者のコメントだけに絞り込む | コメントから 1〜2 手 |
| 読み仮名・メモを登録する | コメントから 2 手で入力を始められる。配信中でも流れを止めずにできる |
| 配信の最後に、スパチャ等をくれた人にお礼を言う | 1 手でその配信の時刻順の一覧を出せる。一覧を見ている間も最新のコメントが見える |
| コラボで 2 つの配信のコメントを見る | 準備のときに 2 つの配信に接続しておけば、配信中は操作ゼロ |
| 配信中に使わない操作を隠す・畳む | どれを隠すかを利用者が選べる (固定より、選べるほうがよい) |

## 5. 犠牲にするもの

- **初めて使う人にとっての分かりやすさ**を少し下げ、慣れた人が一瞬で読み取れることを取る。
  ただし、一般的なアプリケーションの UI の慣習の範囲には収める (独自の操作を覚えさせない)
- **広いウィンドウでの見栄え**。広げて使う人は少ない
- **分析 (Analytics) の画面**。使われていないので外す (2026-10-08 に決定)。
  中にあるエクスポート (CSV・JSON) も使ったことがないので一緒に外してよい。
  代わりに欲しいのは、スパチャ等をくれた人の一覧 (配信の最後のお礼、月ごとのお礼の投稿。「機能への影響」)
- **表示件数の細かい選択肢**。表示件数の制限は、性能の低い PC で CPU・メモリの負荷を下げるためのもの。
  その目的に足りる「無制限 (既定)」と「500 件」だけあればよい

## 6. 性格

- 「**引き立て役**」であって「主役」ではない。主役は配信 (配信者とゲーム)。liscov は普段は静かに控え、目を奪わない
- 「**静か**」であって「見落とさせる」ではない。優先順位 1・2 のものが来たときだけは、はっきり分かり、流れても消えない
- 「**慣れた人に速い**」であって「独自の作法を覚えさせる」ではない
- 「**手を借りない**」であって「操作を求める」ではない。配信中は見るだけで足りる

## 7. 成功の判定方法

- **ちらっと見るテスト**: 撮影した画面を 1 秒見て、**操作せずに**次に答えられる
  - 新しく来たスパチャ・ギフト・メンバーシップはあるか。誰からか
  - 新規さんのコメントはあるか
  - 接続は生きているか
  - (2 つの配信を見ているとき) そのコメントはどちらの配信から来たか
- **目を細めるテスト**: 縮小してぼかした画面で、目立つ順が §2 の優先順位と一致する (操作が上位に来ない)
- **実機**: 配信で使い、操作せず、スクロールして戻らずにスパチャ等に反応できる。見落としが起きない。
  配信の最後に、1 手で出した一覧から漏れなくお礼を言える

## 機能への影響 (デザインの範囲を超えるもの)

このブリーフを満たすには、見た目の変更だけでなく、振る舞いの追加・変更が要るものがある。
実装の前に、該当する仕様書 (`docs/specs/`) を更新して合意する。

- 優先順位 1 のものが流れても見落とさない仕組み (操作ゼロで成り立つもの)
- 新規さんの初回コメントの別枠
- 配信の最後のお礼のための、その配信のスパチャ等の時刻順の一覧 (1 手で出せて、最新のコメントと同時に見える)
- 自動スクロールの自動復帰 (操作が無ければ最新に戻る)
- 2 つの配信を見ているときの配信元の表し方の強化 (今は幅 3px の色の棒と配信者名)。
  視聴者情報 (読み仮名・メモ) の配信者が最初の接続に固定されている件の整理 (コラボ相手側の視聴者)
- 認証切れ・外部連携 (WebSocket) の停止を、異常のときだけ目立たせる
- コメントの固定表示 (ピン留め)、コメントからの視聴者の絞り込み
- 配信中に使わない操作を隠す・畳む設定
- 同時接続数・いいね数の取得 (現状は取得していない)
- ウィンドウの最小幅の引き下げ (現状 `tauri.conf.json` の `minWidth: 800` で、§3 の 540px・640px に収まらない)
- 表示件数の選択肢を「無制限・500 件」に減らす
- 分析画面とエクスポートを外す
- 読み仮名・メモをコメント行に出す (仕様 02_chat には書かれているが、2026-10-08 時点で実装に無い)
- 参加型の支援: 参加中の人と参加を待っている人の一覧を、配信中は操作ゼロで見えるようにし、参加型でないときは隠す。
  そのためには、パネルの配置を選べる仕組み (OBS のパネルの配置のカスタマイズに近いもの、または場面ごとの配置の切替) が要るかもしれない。
  参加希望の受け付け方 (コメントの言葉で拾うか、手で足すか) は未決
- 将来: 期間 (月など) を指定して、スパチャ等をくれた人の一覧を出す (コミュニティ投稿でのお礼用。今は配信単位でしか見られない)
