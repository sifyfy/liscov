# ADR-007: チャットの取得の間隔を、空振りに応じて延ばす

## ステータス

承認

## コンテキスト

チャットの取得 (InnerTube の `get_live_chat`) は、成功している間ずっと 1,500ms の固定間隔で行っていた。
制約「ポーリング間隔は1,500ms」(02_chat.md) で固定していた。

YouTube は応答の continuation に `timeoutMs` を付けて、次に取りに来るまでの間隔を指示している
(2026-10 の実際の配信の生レスポンスでは、`invalidationContinuationData` の `timeoutMs` はすべて 10000)。
YouTube 公式の画面は、新しいコメントの押し通知 (`invalidationId`) を受けて取りに行き、
`timeoutMs` は通知が来ないときの保険として使っている。liscov は押し通知を受けないので、固定の 1,500ms で取っていた。

固定の間隔だと、コメントが途切れている間も 1,500ms ごとに取り続ける。
接続は最大 32 で、どの接続も同じ間隔で取る。

## 決定

- 下限は 1,500ms のまま。新しいメッセージが届いた後と、空振り (成功・新しいメッセージ 0 件) の 1 回目は 1,500ms で取る
- 空振りの 2 回目から 1 回ごとに 1,000ms ずつ延ばす
- 上限は、その応答の `timeoutMs`。無ければ 10,000ms
- 失敗が続いたときの延長 (「取得に失敗したとき」) は今までどおり。失敗は空振りに数えない

## 理由

### 検討した選択肢

| 選択肢 | メリット | デメリット |
|-------|---------|-----------|
| A. 1,500ms 固定のまま | 単純。遅れは常に最大 1.5 秒 | コメントが途切れている間も取り続ける。YouTube の指示より 6 倍以上多く取る |
| B. `timeoutMs` に従う (固定 10 秒) | YouTube の指示どおり。取得の回数が最も少ない | コメントが続いていても最大 10 秒遅れる。配信中に読み上げや一覧が遅れる |
| C. 空振りに応じて 1,500ms から延ばし、上限を `timeoutMs` にする | コメントが続いている間は A と同じ速さ。途切れている間は B に近い回数 | 静かな状態から最初に届くコメントが、最大で上限の秒数遅れる |
| C の上限を 5 秒や 3 秒にする | 静かな状態からの最初のコメントの遅れが小さい | YouTube の指示より多く取る |

### 採用理由

配信中に効くのはコメントが続いている間の速さで、C は A と同じ速さを保つ。
上限はシフィさんが YouTube の指示どおり `timeoutMs` を選んだ (2026-10-12)。
静かな状態からの最初のコメントの遅れは、押し通知 (実験的に別途追加する予定) で縮める。

## 影響

- 02_chat.md: 制約の書き換え、「取得の間隔」の追加、「取得に失敗したとき」「設定値」「チャット監視タスク」の更新
- バックエンド: `InnerTubeClient::fetch_chat` が採用した continuation の `timeoutMs` を返し、監視ループの待ちの計算が空振りの回数と `timeoutMs` を使う
- モックサーバー: 応答の `timeoutMs` を E2E から変えられるようにする (今は 5000 固定)。
  既定のままだと、待ちが延びて既存の E2E が遅くなるため
- 他機能: 読み上げ・WebSocket・DB は届いたメッセージを処理するだけで、間隔には依存しない
